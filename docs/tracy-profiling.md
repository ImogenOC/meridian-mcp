# Tracy profiling

Tracy support is an Experimental development-mode opt-in. Set `MERIDIAN_MCP_TRACY=byond` only with a helper manifest produced from the pinned clean revisions by `scripts/build-tracy-helpers.ps1`. Preparation copies the hash-verified x86 hook beside the DMB; it does not edit the DMB or either upstream checkout.

## Tool workflow

1. `dm_tracy_prepare` copies the verified hook beside one contained DMB. It is idempotent for an identical file and refuses replacement unless explicitly requested.
2. `dm_tracy_launch` requires an existing contained `experiment_directory`, writes an active integrity journal before starting either process, then starts one MCP-owned DreamDaemon and persistent collector on private loopback. Success requires producer progress and records executable, workload-draft, and exact Meridian-MCP build identity. BYOND identity uses the build reported by the connected hook after readiness and rejects builds outside the verified hook manifest range. For Meridian-Rift, supply a contained `config_directory` whose `config.txt` or `dev_overrides.txt` explicitly enables `RESUME_AFTER_INITIALIZATIONS`. Its complete bounded file set is hash-bound into launch identity. `wake_sleeping_world` defaults to true. Launch waits up to `initialization_timeout_ms` (180 seconds by default, 300 seconds maximum) for the fixed initialization-complete marker, waits beyond the offline-sleep tick, sends one post-initialization Topic request over the owned loopback game port, and requires DreamDaemon to process it. The result is retained as `runtime_wake` in launch, status, and capture-sidecar evidence.
3. `dm_tracy_status` reports both owned lifecycles, the profiler endpoint, current worker purpose/transition, retry count, queue and hook health, capture state, integrity-journal summary, bounded output, and the last structured failure.
4. `dm_tracy_capture` records one uniquely named phase/iteration window. Drain-to-capture handoff retries one transient connection failure within the fixed connection ceiling, and measurement time begins only after connection and named queue-health readiness. A valid capture is atomically published as `name.tracy` with `name.tracy.meridian.json`. An invalid trace is retained only under the experiment's `.meridian-tracy-diagnostics` directory with `authoritative: false`; it never enters capture records or statistics. A failure before the window starts leaves the phase iteration reusable. Once a window starts, its iteration is consumed even if validation fails.
5. `dm_tracy_hotspots` ranks exact proc/file/line identities by inclusive time, self time, count, or maximum duration. Only complete zones in the sidecar's half-open range are analyzed.
6. `dm_tracy_zone` returns count, inclusive/self totals, extrema, and p50/p95/p99 for one exact profiled proc name, keeping different source identities separate.
7. `dm_tracy_frame_stats` reports count, mean, extrema, and nearest-rank p50/p95/p99 for complete `ServerTick` frames in the authoritative range.
8. `dm_tracy_compare` checks technical and workload compatibility before computing bounded exact-identity deltas. Same-experiment/same-phase is the default. Cross-experiment comparison must be requested explicitly and still requires matching executable, workload, phase, and memory-role dimensions.
9. `dm_tracy_control_stats` accepts 3-20 unique trace/sidecar pairs, rejects incompatible or incomplete controls, selects a requested per-trace frame or exact-zone percentile, and calculates a deterministic distribution and noise envelope across controls.
10. `dm_tracy_stop` records pre-stop integrity, cancels an active window, stops the collector and owned DreamDaemon, finishes the complete role-specific memory series, writes the experiment-complete manifest, records post-stop integrity, and only then finalizes the journal. Integrity failure never prevents owned-process shutdown and instead returns `workspace_integrity_violation` with an unfinished recovery journal. Unconfirmed collector cleanup retains its ownership and the active journal for retry; a protocol error can be tolerated only after cleanup is confirmed.

Collector requests apply one deadline to writer admission, the complete frame write and the response. Cancellation removes pending requests; abandoning a partial write closes the transport. Fully written abandoned requests permit one late response, with a bounded 256-ID history. Response bodies are limited to 4 MiB before a newline arrives, and stderr is drained into a bounded UTF-8-safe tail. Collector stop schedules independent owned-child termination before attempting protocol shutdown, so blocked stdin cannot indefinitely prevent cleanup. Deadline expiry can precede operating-system confirmation and returns an error rather than claiming the process has stopped.

Offline analysis does not require a parsed DreamMaker environment. When one is active, matching file/line results receive additive source-correlation metadata; measurements are never rewritten.

## Meridian-Rift headless wake

Meridian-Rift sets `world.sleep_offline = TRUE` and immediately calls `sleep(1 TICKS)` before the line that checks `RESUME_AFTER_INITIALIZATIONS`. With zero connected players, the world can suspend at that yield, so `RESUME_AFTER_INITIALIZATIONS` alone is insufficient: the code that would clear offline sleep has not run yet. An idle DreamDaemon process, a live Tracy transport, or a successful native hook handshake does not prove that the DM scheduler is advancing.

The MCP does not modify Meridian-Rift's human-authored configuration or attach to an existing client. The operator supplies a separate profiling configuration directory, explicitly enables `RESUME_AFTER_INITIALIZATIONS`, and authorizes that directory as a workspace root. Meridian-MCP hashes the configuration, waits for the fixed initialization marker, allows five seconds for execution to reach the offline-sleep yield, and tries at most three bounded loopback Topic requests. Launch requires later collector samples to prove sustained producer progress rather than treating a successful request as proof that the scheduler resumed. If Topic is serviced but the scheduler sleeps again, the MCP starts the fixed DreamSeeker executable beside the allowlisted DreamDaemon and holds one process-contained loopback guest until stop. The client executable hash and process identity are included in evidence and its traffic is covered by the existing optional network observations. Failure to observe the marker, launch the client, or sustain progress stops every owned process and returns structured `runtime_wake` evidence; it is never reported as a valid capture. Use `wake_sleeping_world=false` only when measuring the sleeping control intentionally.

Queue backpressure is evidence, not automatic data loss. A positive saturation delta means the producer waited for the consumer and `queue_saturated` is a warning retained in the validation result. It does not invalidate a capture or disqualify a control by itself. A positive dropped-event delta proves loss, so `queue_dropped_events` remains fatal. Queue depth, high-water mark, saturation count, tail-refresh count, and dropped-event count remain present in capture evidence.

## Identity and range semantics

Launch records DMB/RSC and DreamDaemon hashes, BYOND version, hook/helper revisions and hashes, loaded native modules, startup parameters, repository revision and dirty digest. It also records the Meridian-MCP version, source revision, build-time dirty state, target, profile, running executable SHA-256, and derived build ID. Workload identity covers map, seed, configuration profile, sorted feature set, scenario, external run ID, and bounded annotations. Their canonical hashes form an immutable experiment ID. A trace hash mismatch, incomplete MCP build identity, conflicting workload field, reused phase iteration, or incompatible comparison fails before statistics are returned. Comparisons require the same MCP build ID.

Capture intervals are half-open: `[trace_begin_ns, trace_end_ns)`. A complete frame or zone begins at or after the lower bound and ends at or before the upper bound. A partial-first sample crosses the lower boundary, a partial-last sample crosses the upper boundary, and a spanning sample crosses both. Partial samples remain in explicit counts but are excluded from latency distributions. Counts reconcile as `analyzed <= complete <= intersecting <= raw`; exclusions are reported rather than converted to zero-duration samples. Empty complete samples return `insufficient_complete_samples`.

Statistics schema 2 preserves the helper's existing fields and adds experiment/capture/phase identity, authoritative raw range, native range counts, nested statistics, warnings, `window_source`, and `identity_verification`. Legacy traces without a Meridian sidecar use their full trace, report identity verification as unavailable, may be self-compared, and cannot establish an automated control baseline.

Percentiles sort integer nanoseconds and use nearest rank: `ceil(p * n) - 1`, clamped to the sample array. Control standard deviation is the sample standard deviation. A frame or zone metric is noisy when coefficient of variation exceeds `0.10`, or its absolute range exceeds `max(1,000,000 ns, 0.20 * median)`. Any invalid capture, queue drop, fewer than three complete frames, missing exact zone, role-identity failure, or noisy requested metric makes `establishes_control_baseline` false. Lossless queue saturation remains a warning and does not disqualify the baseline by itself.

## Memory and network evidence

DreamDaemon and collector memory is sampled every 500 ms from launch through stop and is never implicitly summed across roles. Windows records working set, private bytes, and virtual bytes. Linux records RSS and virtual bytes. Each series is bound to PID plus process creation/start identity so PID reuse stops the series. Capture sidecars retain samples inside the capture window plus the nearest sample on either side; the final experiment manifest retains the complete bounded series. Metrics of unlike kinds or operating systems are not directly comparable.

`capture_network` is best effort. Structured evidence is restricted to the configured loopback profiler port and the owned DreamDaemon/collector identities. Listener creation and collector handshake can verify those lifecycle facts, but endpoint observation failures are warnings. `network_isolation_confirmed` and `capture_complete` are always false: this feature does not prove that unrelated processes or traffic were absent.

## Reproducible controls and retained artifacts

`scripts/run-tracy-experiment.ps1` drives prepare, launch, status, a default 30-second boot-excluding warmup, repeated capture, range-aware frame analysis, control statistics, stop, and independent validation through the release MCP entry point. The output directory must be new and contained by the configured roots. `WarmupSeconds` can be changed explicitly, including zero for a deliberate boot-phase experiment.

The owned evidence directory contains `experiment.json`, `control-stats.json`, `validation.json`, per-control summaries, `evidence-index.json`, and the local trace/sidecar pairs. Raw `.tracy` files remain local. Workflow uploads explicitly exclude `**/*.tracy`; the index records their hashes so an operator can retain or transfer them deliberately. `scripts/validate-tracy-evidence.ps1` performs no launch and independently rehashes the pairs, verifies immutable identity/ranges, role-specific memory, honest network disclaimers, unique iterations, and control eligibility.

The same directory contains `.meridian-tracy-session.json`. Its paths and observations are repository-relative. A prior active journal blocks reuse of that directory with `recovery_required`; a finalized journal may be replaced by a new explicitly requested session. The profiler never repairs, reverts, or deletes a non-owned source change detected by the journal.

Windows and Ubuntu native results and Windows/Ubuntu live BYOND results are independent evidence. Tracy compatibility remains Experimental until the documented repeated-control live acceptance and hosted platform gates are green; a local native or short-window pass alone does not promote it.
